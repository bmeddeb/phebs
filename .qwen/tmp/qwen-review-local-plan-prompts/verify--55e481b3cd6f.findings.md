# Verification shard 1 — findings R1-1 .. R1-8

## R1-1 [Critical, confidence high] — Orphaned transition marker permanently wedges whole-search publication
- File: internal/focusedindex/search_generation.go:345 (marker write; recovery gate at internal/sync/reconcile.go:369-373; failPublication gate at internal/indexer/indexer.go:493-496)
- Anchor: `return WriteControlFile(filepath.Join(indexDir, searchGenerationMarkerName(marker.Repository)), marker)`
- Issue: The search transition marker is created with WriteControlFile (O_WRONLY|O_CREATE|O_EXCL). If the process dies after prepareSearchGenerationTransition writes the marker but before completeSearchGenerationTransition -> startPublication installs the `.publishing` marker, nothing ever recovers the state: reclaimCommittedPublicationMarkers skips repos where !IsPublishing (no publishing marker exists), CleanupAbandonedLifecycle does not match the transition-marker name, and failPublication returns early when !IsPublishing. Every later PublishWholeGeneration fails at writeSearchGenerationMarker with EEXIST, forever. A torn marker additionally makes Rollback/Recover hard-error on decode.
- Failure scenario (claim under test): kill -9 between writeSearchGenerationMarker and startPublication -> durable state = transition marker present, no publishing marker, root/flat/store untouched -> repository can never be whole-search-reindexed again until manual file deletion. Agent 1c claims empirical reproduction with a throwaway in-package test (publish A, create candidate B + prepare only, then PublishWholeGeneration for C failed with "file exists").
- Suggested fix per finder: write the marker via replaceSearchControlFile (temp+fsync+rename), and/or run RecoverSearchPublication when a transition marker exists without a publishing marker, and/or let failPublication's whole rollback run when a marker exists even if !IsPublishing.

## R1-2 [Critical, confidence high] — Empty `collecting-*` directory permanently wedges the search-generation collector
- File: internal/focusedindex/search_generation_lifecycle.go:348 (exit arithmetic) and internal/focusedindex/search_generation_lifecycle.go:176-180 (receipt read before delete step)
- Anchor (arithmetic): `if more || deleted == budget { return deleted, false, nil }`
- Anchor (receipt read): `if _, err := readSearchLifecycleReceipt( filepath.Join(repositoryDirectory, candidate.name), result.Cursor, candidate.digest, ); err != nil { return result, err }`
- Issue, trigger A (no crash needed): when the final deletion step starts with exactly `budget` entries (budget-1 data files + generation.json receipt, receipt deleted last by priority), the loop drains all of them and exits naturally with deleted == budget; the post-loop condition then returns complete=false without the os.Remove(directory), stranding an empty collecting-* directory whose receipt is gone. Trigger condition on data-file count D: D ≡ budget-1 (mod budget) — e.g. D=15 with production MaxDeletesPerTick=16, or the minimal 5-file generation at budget 2.
- Issue, trigger B (crash): kill -9 between removing the last entry (receipt last) and os.Remove(directory) in deleteSearchGenerationStep leaves the same empty-directory state.
- Failure scenario (claim under test): the next sweep of that namespace enters the collecting branch, calls readSearchLifecycleReceipt on the empty directory, gets "focused control file is missing, special, or exceeds its limit" (not os.ErrNotExist), and returns the error; the controller does not advance the cursor on error, so every future turn hits the same error: lifecycle collection is permanently wedged for the namespace (claim: fleet-wide, since the owner returns the error), stale generations accumulate to the 64-generation cap, and admitSearchGenerationGrowth then blocks new publications for that repository. Agent chunk-8 claims empirical proof via a temporary in-package probe (budget 2, 5 data files + receipt: turns 0-2 deleted 2 files each, turn 3 failed permanently with the empty collecting directory remaining); the existing lifecycle test avoids the residue class because its fixture has D=6 with budget 2 (6 mod 2 = 0).
- Suggested fix per finders: change the exit condition to `if more { return deleted, false, nil }` (directory removal must not be counted against the budget or it trips controller validation result.Deleted > limits.Deletes), AND/OR treat a missing receipt in the collecting drain path as "proceed to deleteSearchGenerationStep" rather than a hard error.

## R1-3 [Critical, confidence high] — Candidate generation directory is unprotected from lifecycle sweep between rename and marker write
- File: internal/focusedindex/publication.go:138-155
- Anchor: `marker, err := prepareSearchGenerationTransition( ctx, indexDir, repository, candidate, )`
- Issue: createImmutableSearchGeneration renames the candidate into search-generations/<repo>/<digest> before prepareSearchGenerationTransition writes the marker that protects it. The lifecycle sweep holds only the shared mutation lock (the indexer holds the same shared lock across publication), so sweep and publication run concurrently. In the window between the rename and the marker write the candidate is referenced by no root, no marker, and no pin.
- Failure scenario (claim under test): on a second-or-later whole-search replacement the namespace holds current + prior; after the candidate rename it holds 3 generation directories, disabling the sweep's age-skip gate (`now.Sub(modified) < MaxAge && len(generations) <= 2`); the newest (candidate) directory matches neither root.Current/root.Prior nor any marker (not yet written) nor any reader pin, passes searchGenerationLifecycleFence, is renamed to collecting-* and drained. installStableSearchGeneration then fails, rollback restores the prior generation, and the completed multi-GiB build is discarded and must be rebuilt. prepareSearchGenerationTransition widens the window by fully re-validating and re-measuring the current generation before writing the marker. Outcome is fail-closed (no corruption), probability per publication is low (ms-scale window vs periodic sweep), but the window recurs on every whole-search replacement.
- Suggested fix per finders: pin the candidate across the publication window (pins.Acquire(repository, candidate.GenerationDigest) with defer Release, sweep already consults pins.Pinned), or make the candidate discoverable only after the marker protects it (rename from a hidden/stage name), or have the sweep take the exclusive mutation lock.

## R1-4 [Critical, confidence high] — Per-repository namespace directories are never pruned; at 4,096 namespaces the base fence halts all collection
- File: internal/focusedindex/search_generation_lifecycle.go:399 (boundedSearchDirectory fence over the base directory; SweepSearchGenerationLifecycle never removes emptied namespace dirs)
- Anchor: `if len(entries) > limit { return nil, errors.New("search lifecycle directory exceeds policy") }`
- Issue: every repository that ever publishes a whole-search generation permanently creates search-generations/<repo-hash>/. When a repository is deleted, removeRepositoryArtifacts removes the root/marker controls and the sweep drains the generation directories, but nothing ever removes the now-empty namespace directory itself.
- Failure scenario (claim under test): after 4,096+1 distinct repositories have published over the installation's lifetime (the project's own Epic 41 envelope measures 10,000 services), boundedSearchDirectory(base, MaxSearchLifecycleRepositories) errors before any namespace is examined, SweepSearchGenerationLifecycle returns an error, the owner returns the input cursor so the durable cursor never advances, and the error repeats every fair turn forever: no stale generation in any repository is ever collected again; prior/collecting generations accumulate without bound on disk.
- Suggested fix per finder: at the end of a namespace turn, when the namespace's generation entries are empty, os.Remove(repositoryDirectory) so drained namespaces are pruned at fair-cursor pace.

## R1-7 [Suggestion, confidence high] — Three full-content validations per publication, under the shared mutation lock
- File: internal/focusedindex/search_generation.go:758-760 (also :547 in createImmutableSearchGeneration and :799 in prepareSearchGenerationTransition)
- Anchor: `receipt, err := validateImmutableSearchGeneration( ctx, indexDir, repository, ref.GenerationDigest, )`
- Issue: each whole-search publication runs full-content validation three times — stage (createImmutableSearchGeneration), previous current generation (prepareSearchGenerationTransition), and candidate again (installStableSearchGeneration) — each hashing every shard byte and re-parsing every source record; the pre-diff publication performed zero content reads (rename + fsync only). Rollback and crash recovery pay the same cost.
- Failure scenario (claim under test): at retained scale (up to ~48 GiB/generation, 256 shards x 512 MiB, 16,384 members), ~3 generation-equivalents of SHA-256 + full JSON parse per publication (claimed up to ~144 GiB of reads) while holding the shared mutation lock, blocking lifecycle collection turns and other publications; the ADR budgets one candidate validation, not three passes.
- Suggested fix per finder: keep full-content validation once at stage time; use identity/receipt-only rechecks for pre-install and previous-root fences (ValidateWholeReceipt exists for that role); reserve full re-validation for paths adopting bytes this process did not build (legacy adoption, recovery).

## R1-8 [Suggestion, confidence high] — Lifecycle test loop breaks on its first turn; the collecting-resumption lane is never exercised

(Note: R1-2's residue class is one such regression and currently has no test that could catch it.)
- Suggested fix per finder: break only when both directoryA and collecting-<directoryA> are gone.
