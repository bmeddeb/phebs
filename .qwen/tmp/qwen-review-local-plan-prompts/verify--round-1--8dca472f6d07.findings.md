# Round-1 reverse-audit findings to verify — R1-15 .. R1-21

## R1-15 [Critical, confidence low] — Lifecycle root survives whole-search -> focused posture flip, pinning up to 96 GiB
- File: internal/focusedindex/publication.go:194-195
- Anchor: `searchLifecycleRoot := SearchGenerationRootName(repository) searchTransition := searchGenerationMarkerName(repository)`
- Issue: Repository R indexed whole-search (root phebs-search-lifecycle-<key>.json exists; search-generations/<key>/ holds current+prior). Operator flips R to focused posture. PublishFocused calls removeRepositoryArtifacts(ctx, indexDir, R, true), which deletes the flat whole-search artifacts but the new preserveMarker clause retains the root. Nothing ever removes the root afterwards: the searcher consults roots only for non-focused repos (searcher.go:1073), reconcileFocusedArtifacts skips phebs-search-lifecycle-* names, RecoverSearchPublication requires a marker, RemoveRepository runs only on repo deletion or focused-publication failure. SweepSearchGenerationLifecycle protects root.Current/root.Prior unconditionally (filesystem-only, never consults the store), so those generations are never collected while R stays focused — up to 48 GiB logical x 2 generations.
- Failure scenario (claim under test): posture flip permanently retains up to 96 GiB of immutable generation bytes, invisible (lifecycle status reports them as ordinary protected retention), until the repository is deleted; contradicts the diff's documented contract that stale generations are collected. Distinct from R1-4: even with empty-namespace pruning, this namespace never empties because the root protects its contents.
- Suggested fix per finder: split the preserveMarker flag so installStableSearchGeneration keeps root+marker while PublishFocused keeps only the transition marker, or remove the root explicitly in the indexer's focused commit-success path / reconcile's posture-mismatch repair.

## R1-16 [Critical, confidence low] — Ambiguous-commit re-read failure leaves committed row permanently diverged from disk
- File: internal/indexer/indexer.go:460-467
- Anchor: `if unit == nil { rollbackErr := focusedindex.RollbackSearchPublication(ctx, indexDir, repo.Name) rootPath := filepath.Join(indexDir, focusedindex.SearchGenerationRootName(repo.Name)) _, rootErr := os.Lstat(rootPath) var clearErr error if errors.Is(rootErr, os.ErrNotExist) { clearErr = ix.Store.ClearRepoIndexState(ctx, repo.Name) }`
- Issue: when the ambiguous-commit re-read itself fails (readErr != nil), the whole-search branch resolves the ambiguity as "commit definitely failed": it rolls back (destroying the transition marker that startup RecoverSearchPublication needs) and skips ClearRepoIndexState because the restored prior root exists.
- Failure scenario (claim under test): publication succeeds, SetRepoIndexedState commits in SurrealDB but its response is lost (WS disconnect/timeout), the immediately following GetRepo also fails (connection still down); rollback restores prior generation A and removes both markers; root existence skips the state clear. When the DB recovers, the row claims B while disk serves A, terminally: sync's no-op short-circuit blocks rebuilds; startup recovery is a no-op (no marker); the new pin fence in searcher.go returns errWholeGenerationChanged ("search-generation root is stale") BEFORE acquireIfStale, so the whole-repair path that enqueues forced rebuilds is never reached; every query whose repo set includes R fails until a new commit or manual forced index job. The focused lane does not have this hole because it attempts ClearRepoIndexState unconditionally.
- Suggested fix per finder: treat readErr != nil as unresolved ambiguity — clear repo index state (or skip the rollback and leave the marker for RecoverSearchPublication to select the generation matching the durable row).

## R1-17 [Suggestion, confidence low] — RecoverSearchPublication error continues past the committed-validation retirement path
- File: internal/sync/reconcile.go:378-384
- Anchor: `if recoverErr != nil { errs = append(errs, fmt.Errorf( "recover search generation publication for %s: %w", repo.Name, recoverErr, )) continue }`
- Issue: on RecoverSearchPublication error the branch continues, bypassing the pre-existing committed-validation path that can legally retire the marker.
- Failure scenario (claim under test): legacy whole-search repo (committed whole shards+manifest validate at store revisions R1, no search manifest, no root). Fetch lands R2; first T40.5 publication crashes after startPublication but before root write, leaving marker {candidate: R2, previous: nil} + publishing marker. Every reconcile tick RecoverSearchPublication(wholeRevisions=R1) hits its default case ("matches no committed generation") and the continue skips the fall-through committed check, which would pass (validateWholePublishedContext explicitly allows the publication marker for exactly this retirement) and call FinishPublication, keeping R1 searchable. Instead the marker persists: repo stays IsPublishing, whole-search queries fail with errWholeGenerationChanged; clearing requires a successful indexer retry (full rebuild -> EEXIST -> failPublication -> RollbackSearchPublication Previous==nil -> removeRepositoryArtifacts deletes the valid R1 artifacts too -> ClearRepoIndexState -> second full rebuild) — >=1 wasted whole-repository zoekt build plus an unsearchable window; indefinite if admission gating or a paused repo blocks index runs.
- Suggested fix per finder: on recoverErr fall through to committed validation instead of continue (or have the no-marker-match default return (false, nil), reserving errors for I/O failures).

## R1-18 [Suggestion, confidence low] — Deep validation demands exact allocated-byte equality, breaking cross-filesystem migration
- File: internal/focusedindex/search_generation.go:633-636
- Anchor: `logical, allocated, allocatedState, err := measureSearchGeneration(directory, files, shards) if err != nil || logical != receipt.LogicalBytes || allocatedState != receipt.AllocatedState || (allocatedState == "exact" && allocated != receipt.AllocatedBytes) ||`
- Issue: validateImmutableSearchGeneration re-measures st_blocks and requires exact equality with the receipt — a filesystem-dependent property, not a content property.
- Failure scenario (claim under test): operator migrates the data directory by copying it to a filesystem with different allocation semantics (ext4 -> btrfs with compression, ext4 -> ZFS). Bytes are identical so content validation passes, but st_blocks differs -> "search generation accounting changed". That poisons every deep-validation path: the next PublishWholeGeneration fails in prepareSearchGenerationTransition (validates root.Current before writing the marker) after paying for a full census + zoekt rebuild; RollbackSearchPublication and RecoverSearchPublication fail too (both enter through installStableSearchGeneration). No self-heal: the root exists so failPublication never clears index state; every head advance rebuilds and fails publication again. The sanctioned backup/restore path is unaffected only because archives deliberately drop generation state and re-adopt.
- Suggested fix per finder: treat allocation as informational — compare only logical bytes, tolerate/re-record allocated drift; keep the bounds fence on carried-forward values.

## R1-19 [Suggestion, confidence low] — Recovery candidate branch hand-rebuilds the prospective root
- File: internal/focusedindex/search_generation.go:899-907
- Anchor: `case sameSearchRevisions(marker.Candidate.Revisions, revisions): selected = marker.Candidate root = SearchGenerationRoot{ Schema: SearchGenerationRootSchema, Repository: repository, Current: selected, }`
- Issue: RecoverSearchPublication's candidate branch reconstructs the root (including the Prior derivation condition) instead of calling prospectiveSearchGenerationRoot(marker), duplicating the root-shape policy in two places ~50 lines apart.
- Failure scenario (claim under test): a future retained-pair policy change applied to prospectiveSearchGenerationRoot but not the recovery branch makes post-crash recovery write a root shape the normal publication path would never write; divergence invisible until a crash makes recovery the active path; writeSearchGenerationRoot validates ref invariants, not policy intent. The previous-match branch legitimately cannot use the helper (root = *marker.Previous), but the candidate branch is a reimplementation.
- Suggested fix per finder: in the candidate branch, selected = marker.Candidate then root, err := prospectiveSearchGenerationRoot(marker).

## R1-20 [Critical, confidence high] — Single benign foreign file permanently wedges all search-generation collection
- File: internal/focusedindex/search_generation_lifecycle.go:93-95 (same class at :54-56 and :327)
- Anchor: `if !entry.IsDir() || entry.Type()&os.ModeSymlink != 0 { return result, errors.New("invalid search lifecycle generation inventory") }`
- Issue: the sweep hard-errors on any unrecognized entry in a swept directory, and lifecycle.Controller.Tick only CAS-persists the owner cursor when result.Err == nil, so the cursor is frozen and every retry re-enters the same namespace and fails identically. Nothing ever removes foreign files under search-generations/ (CleanupAbandonedLifecycle scans only the index root and matches only .phebs-build-*/.phebs-restore-*/.phebs-focus-*). Same wedge inside a collecting directory via deleteSearchGenerationStep's validSearchGenerationEntry rejection (:327).
- Failure scenario (claim under test): on macOS (the project's host/dev platform) an operator opens search-generations/<repo>/ in Finder; Finder writes .DS_Store there (backup tooling drops ._* AppleDouble files). Next lifecycle turn returns "invalid search lifecycle generation inventory" (or the repository-level variant at :54-56, which wedges before any namespace is examined). Outcome: stale-generation collection stops for every repository permanently; each publication cycle orphans a generation directory (up to ~48 GiB at ceilings); disk grows without bound; namespaces reaching 64 directories are refused further publications by admitSearchGenerationGrowth. Distinct from R1-2/R1-4: different trigger, different code site, their fixes do not cover it.
- Suggested fix per finder: treat unrecognized plain regular files as skippable junk (ignore/count/log; remove them in the delete step since they cannot belong to the receipt-validated inventory); keep hard failures for symlinks and unexpected directories.

## R1-21 [Critical, confidence low] — Crash-orphaned stage directories overflow the namespace bounded-read budget and wedge the owner
- File: internal/focusedindex/search_generation_lifecycle.go:399 (+ internal/focusedindex/search_generation.go:468-477, internal/lifecycle/search.go:32-35)
- Anchor: `if len(entries) > limit { return nil, errors.New("search lifecycle directory exceeds policy") }`
- Issue: createImmutableSearchGeneration leaves .stage-<owner>-* directories only on hard crash (deferred RemoveAll covers normal error paths); admitSearchGenerationGrowth skips .stage-/.legacy- entries entirely, so nothing bounds their accumulation; they count against boundedSearchDirectory's MaxSearchRepositoryGenerations+8 = 72-entry namespace budget.
- Failure scenario (claim under test): once one namespace holds >72 combined entries (e.g. a repo at its 64-generation cap plus 9 kill -9'd publications, or fewer generations while lifecycle is disabled and crashes accumulate), boundedSearchDirectory errors BEFORE the sweep's classification loop sees the abandoned stages it exists to collect. Every subsequent search-owner turn hits the same error; Sweep returns the input cursor on error, the controller CASes only on Err == nil, sort.SearchStrings deterministically re-selects the same namespace: permanent, global wedge (no stale generation in any repository is ever collected again), and admitSearchGenerationGrowth uses the same bounded read, so new publications for that repository fail with the policy error even below the generation cap. Distinct from R1-2/R1-4.
- Suggested fix per finder: count .stage-/.legacy- toward the admission bound (or refuse publication once staging dirs exceed a small bound), and/or make an over-budget namespace degradable (skip + advance cursor).
